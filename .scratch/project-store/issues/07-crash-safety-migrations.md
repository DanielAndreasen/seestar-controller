**What to build:** hardening the store — all writes atomic (SQLite transactions, temp+rename for files), the db opens cleanly after a simulated kill mid-write, and a schema version pragma enables future migrations. Demoable: kill a write mid-transaction in a test, reopen, db is consistent.

## Comments

Implemented in `src/seestar_controller/store/schema.py` + `project.py` (exports added in `store/__init__.py`), pure Python stdlib only — no GTK / no link imports, subprocess-enforced in tests.

- **Migration runner** (`schema.py`): `MIGRATIONS: dict[int, tuple[MigrationStep, ...]]` maps from-version -> steps (a step is a SQL string or a callable taking the conn — SQLite has no `ADD COLUMN IF NOT EXISTS`); `migrate_db(conn) -> int` reads `PRAGMA user_version`, applies pending migrations in ascending order, each in ONE explicit transaction (`BEGIN IMMEDIATE` … `COMMIT`) that also contains its `user_version` bump — an explicit `BEGIN` is used because py3.12 legacy isolation autocommits DDL, so a crash mid-migration rolls back completely (DDL included) and the next call re-runs it. Returns `SCHEMA_VERSION`; raises `InvalidProjectError` for `user_version > SCHEMA_VERSION`, negative versions, a missing migration path, or an open transaction on the conn.
- **Version bump 1 -> 2**: `MIGRATIONS = {0: SCHEMA_STATEMENTS, 1: (_add_stars_aperture_columns,)}`. 0->1 creates the schema (`IF NOT EXISTS`, so it also completes a partially created v0 db); 1->2 ALTERs `stars` to add `aperture_radius` / `sky_annulus_inner` / `sky_annulus_outer` **if missing** — dev-build v1 dbs from ticket 04's in-place stars-table extension may lack them (resolves the ticket-04 nit) — via `NOT NULL DEFAULT 4.0 / 8.0 / 12.0` (`STARS_APERTURE_DEFAULTS`), so existing rows are backfilled with a valid default aperture and the columns stay `NOT NULL` exactly like in a fresh v2 db. `initialize_db` creates the v2 schema directly by running `migrate_db` on the fresh (`user_version=0`) connection after setting WAL + foreign keys — fresh creation and migration share one code path.
- **`open_project`** now calls `schema.migrate_db` instead of hard-failing on older versions: the config `schema_version` must still be an int in `1..SCHEMA_VERSION` (else `InvalidProjectError`); the db's `user_version` is authoritative — `> SCHEMA_VERSION` or a corrupt db -> `InvalidProjectError`; a db at version >= 1 must already have all `SCHEMA_TABLES` (clear "missing tables" error), a v0 db gets them from the 0->1 migration; after migrating, all tables are re-checked; the opened db is put in WAL mode (`PRAGMA journal_mode=WAL`, which also covers migrated dbs) with foreign keys ON; if the config's `schema_version` differs from `SCHEMA_VERSION` after the open (a migration happened, or a previous open crashed between the db migration and the mirror write), it is bumped and persisted atomically via `save_config` — both copies of the version are bumped together.
- **Crash-safety spot check**: all mutators already run in `with project.db:` transactions (sessions, the frames phase-2 insert, stars, measurements) and all file writes are temp + fsync + `os.replace` with temp cleanup on any failure incl. `KeyboardInterrupt` (`project.json`, frames, CSV) — verified by reading the code and by the new tests. Stray `*.tmp` files left by a killed process are ignored on open/list (never read, never deleted — the store has no locking, spec out of scope; documented in `project.py`).
- **Exports**: `migrate_db` and `MIGRATIONS` added to `store/__init__.py` (`SCHEMA_VERSION` was already exported).
- **Tests**: `tests/test_store_migrations.py` (22 tests, tmp_path only, no network): (a) v0 empty db inside a valid project layout -> `open_project` migrates to `SCHEMA_VERSION`, tables exist, WAL mode, config mirror bumped on disk, project usable; direct `migrate_db` on a fresh connection; `initialize_db` creates the v2 schema directly. (b) dev-build v1 project with the OLD stars table + one existing row -> open migrates to v2, aperture columns present, row preserved with the default aperture (4.0/8.0/12.0), `load_star_picks` returns it; direct 1->2 migrate; 1->2 is a no-op when the columns already exist (current-build v1 db). (c) `user_version = SCHEMA_VERSION+1` (db side and config side) and negative -> `InvalidProjectError`; `migrate_db` rejects newer/negative versions and open transactions. (d) `KeyboardInterrupt` injected inside the `with project.db:` block of `add_measurement` (on the INSERT) and of `save_star_picks` (on the first INSERT after the DELETE) via a connection proxy -> reopen: no partial rows, old data intact, `PRAGMA integrity_check` ok, WAL recovery works; `KeyboardInterrupt` mid-migration (on a `CREATE TABLE` and on an `ALTER TABLE`) -> full rollback to the previous version, reopen/re-run completes the migration. (e) stray `project.json.*.tmp` / `lightcurve.csv.*.tmp` / `.frame-*.tmp` files -> `open_project` + `list_frames` + `list_projects` ignore them (still on disk, never returned). (f) idempotence: `migrate_db` on a current db executes only the version read (counting proxy); opening a v0 project twice migrates only once (spy sees `user_version` 0 then `SCHEMA_VERSION`); create->open twice never migrates; the crash-between-migration-and-mirror case bumps the config only.
